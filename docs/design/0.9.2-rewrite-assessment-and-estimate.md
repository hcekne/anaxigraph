# AnaxiGraph rewrite comparison and bottom up estimate

**Date:** 24 October 2026

**Status:** Decision analysis recorded on 24 October. On 25 October the maintainer selected a clean
replacement core and rejected capability freezing: build the useful MVP and add features selectively.
Implementation now starts in [AnaxiGraph V2](../../anaxigraph-v2/README.md). The estimates below
retain their original scopes and are not a claim that this smaller first milestone delivers them.

**Current implementation:** 0.9.1; 79,060 production physical lines in 423 code files. The source
comparison includes the roadmap and source-checked review through `5a12b3c`; its production code is
unchanged from the audited 0.9.1 baseline.

The [complete supplied proposal](../proposals/2026-10-24-from-scratch-proposal.md) gives a strong
product direction: help an agent place a change, preserve obligations and make the next change
straightforward. It also describes a narrower first delivery than the full product previously
requested. Those scopes must stay separate when estimating size or deciding to rewrite.

My recommendation is to evaluate a **clean replacement core with deliberate reuse of proven parts**,
against a consolidation candidate under the same behavior contract. A destructive reset is not yet
justified by a proposal and an estimated line count. Equally, existing implementation effort is not
an argument for retaining duplicate execution and state machinery.

The arithmetic is in the [machine-readable work-package worksheet](0.9.2-rewrite-code-estimate.json).
Its central estimates are approximately **16,000 production lines for the first Python milestone**,
**22,000 for the complete pasted proposal**, and **37,000 for the broader required product**.
Tests, delivery code and evaluation tooling are additional.

## What changes compared with the 0.9.2 plan

The [0.9.2 request](0.9.2-performance-and-architecture-request.md) already proposes one graph,
concise annotations, one bounded runner, complete blind product contracts, exhaustive pattern
screening and source-aware retain/change/delete planning. The new proposal makes everyday coding
outcomes and their evaluation more explicit. That strengthens the plan.

The [source-checked change-loop review](../change-loop-review-2026-10.md), added to `main` while
this estimate was being prepared, independently identifies concrete gaps: unresolved rules that
look passed, worsening findings omitted from comparison, governing rules lost during ranking,
missing edit-plan assessment, unattributed check evidence and two freshness defects. Integrate its
repairs into the existing scope; do not create a second roadmap or evaluation engine.

The proposal expressly says it has not inspected AnaxiGraph. Agreement with existing primitives is
useful, not a claim by its author that all those capabilities are missing.

The main gain over our earlier plan is a clearer everyday change loop: retrieve an existing
capability, assess the intended edit, compare the resulting patch and check the next change. That
gives the graph an outcome to support beyond completing mapping/review jobs. A single result record
for these actions can also reduce divergent interpretations between agents and the dashboard.

The main cost is additional analysis and evidence lifecycle: accepted intent, behavioral contracts,
dirty-worktree results and check receipts all need invalidation and honest uncertainty. These can
make the product larger if added alongside the existing engines instead of replacing responsibilities.
A task-centered interface must also retain open-ended architecture exploration; an agent's immediate
task will not necessarily expose a useful cross-system redesign. Fresh Eyes and exhaustive pattern
screening serve that broader purpose. The supplied smaller first milestone would lose those
capabilities, richer workflows and multiple languages until they are deliberately restored.

General node/edge/contract corrections need a uniform lifecycle only where there is a real use.
Current milestone `verified` accepts nonblank **reported evidence**; it does not execute or independently

The service can collect CI or coding-agent receipts while remaining read-only with respect to the
analyzed project. Direct project-test execution is a separate configured capability. Its command,
working directory, environment, deadline, output budget and candidate fingerprint need explicit
handling. Launching a model CLI is not the same operation as running the target repository's tests.
For the existing 0.9.2 plan, follow the source-checked review's **receipt-only** choice: agents or CI
run project checks; AnaxiGraph validates their attribution and reports their origin. The quoted
proposal's broader check-runner option is a separate estimate allowance, not a decision to add
target-code execution to the service. The verification budget also covers robust receipt handling
when that option is omitted; final sizing should settle the exact interface.

Immutable facts and snapshot deltas already exist, but normal reuse begins from the same repository's
latest snapshot. A shared immutable base across worktrees must demonstrate lower storage/parsing/model

## Scope and counting assumptions

These are bottom-up engineering estimates of **final maintained code**, not a measured prototype,
newly typed lines, elapsed implementation time or a statistical confidence interval. Reused code
still counts in the resulting product. The estimates were independently decomposed across backend,
frontend, transports and migration, then reconciled so the same responsibility is not added twice.

Count readable physical production Python, JavaScript, TypeScript, CSS and HTML, including normal
comments, prompt/schema definitions and embedded SQL. If equivalent application logic is moved to
SQL, JSON, generated output or another maintained package, disclose and count it rather than
claiming it disappeared. Third-party libraries and generated data are excluded from custom source;
report dependency and fixture/storage burdens separately.

Assumptions:

- Python is the first analyzed language and the application remains a local modular monolith.
- SQLite/FTS, mature parsing primitives, FastAPI/MCP and validation libraries provide infrastructure.
  We implement scoped resolution and honest unknowns, not a new general-purpose language compiler.
- One application owner accepts graph/annotation results. Workers do not invent independent stores.
- One durable runner supplies attempts, leases, retries, cancellation and conditional publication.
- Finished records and mutable work attempts have separate meanings; current state and bounded
  comparisons are the default, rather than arbitrary historical SQL replay.
- Full quoted scope includes both native model adapters, physical worktree sharing, general plan
  assessment, contract/intent corrections, some resource relations and check receipts.
- The section-12 milestone defers physical sharing, general plan assessment, deeper resource
  discovery and a second model adapter. It still identifies the exact working checkout.
- A curated pattern set is supported by task retrieval/assessment; exhaustive project-wide screening
  and blind Fresh Eyes are separately priced additions.
- The broader required profile retains one sentence per supplied function, as well as each module's
  sentence and short paragraph. The quoted proposal permits selected function notes instead.
  Complete function coverage and its validation fit the annotation work package; no separate
  narrative store or duplicate description generator is assumed.
- No custom arbitrary-scale graph editor, distributed worker platform, PostgreSQL deployment or
  full static proof of dynamic Python behavior is included.

An isolated UI, a few API wrappers or an "analysis engine" box do not constitute a complete estimate.
The tables include data lifecycle, failures, integration and uncertainty reporting that those boxes hide.

## Important uncertainty and sizing limits

The largest uncertainties are reference-resolution precision, worktree/context reuse, cancellation
and stale-result races, model/provider protocol behavior, check-execution trust and compatibility.
The high budgets represent more difficult implementations of those responsibilities, not a promise
that unforeseen scope is covered. Migrating all old modes indefinitely or building sound dynamic
analysis for every language would be a larger project.

Code size is not implementation effort. Reading existing behavior, evaluating model usefulness,
operating two implementations temporarily, reconciling paid data and retiring the old paths can
cost substantial work even when the final product is smaller. A rewrite also does not automatically
fix prompt omissions: the same complete functional contract and acceptance examples are required.

## Decision framework

### Freeze the behavior contract first

Use two scopes explicitly: the small Python prototype and the intended shipped product. For the
latter, retain compact graph/contract traversal, full declared catalogue coverage, blind Fresh Eyes,
source-aware planning, visual manual/full workflows, JS/TS and Git-portable results unless the
maintainer deliberately chooses a narrower product. Preserve optional direction and agent defaults.

Specify exact snapshot/working-tree identity; facts versus inference/intent/proposals; input-bound
publication; accepted corrections; cancellation and failed-only recovery; check-result origins;
current storage limits; and the old-result migration. Preserve the new age-independent dead-code
contract. Do not preserve known bugs such as dropped Fresh Eyes requirements.

### Compare the real choices

| Choice | When it is attractive | Main failure mode |
| --- | --- | --- |
| Consolidate existing core | Proven parsing/integration/data paths can be retained while execution and state duplication is removed | New facades leave the same underlying complexity and source count. |
| Clean replacement core with selected reuse | Current state/orchestration boundaries obstruct simplification; independent parsers, transport/visual primitives and release tools remain useful | Old and new engines both remain indefinitely, or old code is hidden behind a new API. |
| Entire new implementation | Existing dependencies and internal assumptions prevent the agreed contract and a complete measured replacement is credible | Recreating edge cases, migration and compatibility consumes the apparent savings. |
| Deliberately narrower new product | The maintainer accepts fewer capabilities for much lower complexity | A scope cut is presented as a feature-equivalent rewrite. |

I favor the **replacement-core experiment**, with consolidation as its comparator. Start with a
fresh responsibility model, but reuse correct pieces where they fit. Discarding a tested parser,
known CLI protocol behavior, useful visual component or working release publisher has no inherent value.

### Hard criteria precede scoring

A shipped candidate must satisfy these before a smaller code count or attractive demo can win:

- Preserve the agreed capability set and paid records/provenance.
- Keep exact checkout/baseline identity and reject stale publication; compare dirty linked worktrees correctly.
- Preserve required validation even when the graph is incomplete; distinguish executed, reported,
  stale, failed and unresolved evidence.
- Keep blind design workers free of current implementation/source context, and give every design,
  comparison and reviewer the complete relevant functional contract.
- Account for every declared module/catalogue pair, including negative and unknown decisions.
- Resume only missing work and respect the existing storage boundaries over repeated cycles.

The current unmodified 0.9.1 baseline does not meet every new requirement. Both proposed candidates
must repair the same deficiencies; a weak baseline does not justify accepting a weak rewrite.

### Build one representative vertical slice

This is a proposed follow-up experiment, not work performed for this estimate:

1. Analyze a mixed Python/TypeScript fixture with a cross-file provider contract, registered callback
   and intentionally unresolved dynamic reference. Compare facts against known fixture truth.
2. Inspect responsibility → interface → obligation → consumer/test using bounded saved evidence.
3. Prepare and assess an implementation-only change and a contract-breaking change; demonstrate
   different obligations and a real reuse opportunity rather than duplicated business logic.
4. Edit a dirty linked worktree, retain its baseline, reject another checkout's result, and invalidate
   caller guidance when only a callee contract changes.
5. Supply passing, failing and stale check receipts. Optionally execute an explicitly configured
   check; bind its result to candidate bytes and scope.
6. Correct a claim, change source, and show the resulting contradiction or need for review without
   silently losing the accepted intent.
7. Import the real 0.9.1 record into a different clone path, preserve paid data, and verify repeated
   unchanged cycles add no storage or model calls.
8. Interrupt independent semantic batches, resume missing work, and demonstrate overlapping actual
   calls with labelled reconciliation.
9. Exercise pattern opportunities across several families and healthy controls; use two different
   legacy implementations with the same blind product contract to check Fresh Eyes anchoring.

Consolidation and replacement should use the same application contract, fixtures, models and budgets.
New action names can be a facade for either and must not prejudice the result. Count all maintained
transitive application code: a thin replacement that imports the old engine has not eliminated it.

### Record evidence before choosing the implementation route

| Dimension | Evidence needed |
| --- | --- |
| Correctness and usefulness | Fixture precision/recall, honest unknowns, task success, reuse/placement quality, required-check recall and source/human adjudication |
| Simplicity | Production lines/bytes/files under the same definition; mutable state owners, persistent schemas, execution paths and duplicated projections |
| Responsiveness | Cold graph availability, one-file update, p50/p95 bounded reads and time to a useful change brief |
| AI work | Actual calls, retries, tokens, time, recovered work and provider throttling, including setup and refresh |
| Data and operations | Retained/transient bytes, portable count, repeated-cycle stability, migration and rollback |
| Subsequent change | A fresh agent extends feature A with feature B under comparable models and resources |

Optional weights such as correctness/usefulness 35%, simplicity 25%, latency 20%, cost/storage 10%
and migration risk 10% are a declared decision policy, not measured scores. Leave scores blank until
there is evidence. No aggregate score can override a failed required behavior.

Choose replacement when the slice meets hard criteria, demonstrates genuinely simpler state and
execution, and supports a credible full-product budget and migration. Choose consolidation when
it achieves comparable outcomes with materially less transition work. A complete fresh implementation
is justified only if the retained architecture actually prevents that result; do not infer this
solely from current line count or frustration. If the smaller product is preferable, make its removed
capabilities an explicit decision.

## Evaluation of the supplied references

The engineering references are useful precedents, not implementation-size or product-success proofs.
[Tree-sitter](https://tree-sitter.github.io/tree-sitter/) supports incremental syntax work; a separate
resolution layer still needs honest ambiguity. [Aider's repository map](https://aider.chat/docs/repomap.html)
illustrates context selection under a budget. [ArchUnit's freezing mechanism](https://www.archunit.org/userguide/html/000_Index.html)
records existing violations and tightens that baseline; the present repository already has such
ratchet concepts. [Dependency-cruiser](https://github.com/sverweij/dependency-cruiser) and
[Knip](https://knip.dev/explanations/how-knip-works) are references or language-specific evidence tools,
not reasons to rebuild those analyzers inside AnaxiGraph.

The cited papers are real primary sources. [RepoGraph](https://arxiv.org/html/2410.14684v2) supports
being selective about context in its studied setting. [CodeTaste](https://arxiv.org/html/2603.04177v2)
distinguishes discovering refactorings from executing specified ones.
[CodeThread](https://arxiv.org/html/2606.21804v1) studies downstream maintenance and shows why structural
metrics alone do not settle usefulness. None establishes a universal retrieval depth, a successful
AnaxiGraph rewrite, or our LOC forecast. The supplied star counts are archived as quoted; they are
not a selection criterion here.

Adopt the proposal's four evaluation configurations: ordinary tools, structural map, semantic briefs,
and plan/patch feedback. Keep revisions/tasks/models/resources comparable, include indexing/refresh,
and record whether agents use the advice. Then repeat on a follow-up change with a fresh agent.
This strengthens the 0.9.2 plan's usefulness evaluation without adding a new slow pre-push gate.
The source-checked review starts with three arms (ordinary, structural, full guidance). That is a
valid first comparison; split full guidance into semantic briefs and plan/patch feedback when the
two can be isolated reliably. Keep the four-arm proposal as the fuller attribution experiment.
