# AnaxiGraph — Product Capability Specification

---

## Mission

> **AnaxiGraph is the shared architecture intelligence layer for humans and AI agents. It explains what a software system does and how its parts work together, while guiding future changes toward a cleaner, more coherent design.**
>
> **Understand the system. Guide the agent. Keep the architecture coherent.**

AI-assisted development now adds code faster than any team can absorb it into a coherent architecture. Hidden coupling, duplicated responsibilities, inconsistent abstractions and one-off agent changes quietly turn a working system into one nobody can reason about.

AnaxiGraph is a persistent architecture intelligence layer for a software repository, built for coding agents first and for people equally. It maintains an inspectable understanding of what a repository does, how its parts work together, why they exist and how the design is changing — so that a person exploring the system and an agent acting on it work from the same account of it.

The three promises, expanded:

1. **Understand the system** — a written, evidence-backed account of the repository, from what the whole program is for down to a single named function.
2. **Guide the agent** — answer *where does this change belong* before the change is written, grounded in the repository that actually exists rather than in whatever files happened to land in a context window.
3. **Keep the architecture coherent** — surface what deserves attention, in ranked order, as ordinary sentences that argue their own case and name their own counter-evidence.

In one sentence: *give people and coding agents one living, inspectable understanding of the software, then use it to make the next change fit the system better than an isolated prompt would.*

---

## What this is / what this is not

**It is** a read-only observer of a repository that keeps a durable memory of it, reachable from a browser dashboard, from the command line, and from a connected coding agent — all three returning the same claims with the same evidence and the same stated confidence.

**It is not**:

- a pretty code graph drawn for its own sake;
- a magic architecture score — there is no health grade, letter, index or gauge, by decision;
- another AI reviewer commenting on your diff;
- an autonomous refactoring tool. It never edits, deletes, merges, splits or executes the code it studies, and no result it produces is permission to do so.

Three kinds of statement are kept visibly apart everywhere they appear: **facts read from the code**, **AI-written interpretation**, and **recommendation**. A beginner can read the plain-language conclusion; an expert can audit the evidence behind it. Where the tool cannot see something — wiring that only exists while the program runs, for instance — it says so rather than treating silence as proof.

## Area 1 — Understanding the system

The starting problem is arrival: a person or an agent facing a repository they have not internalised. AnaxiGraph answers by keeping a repository-wide memory that survives across sessions, separating counted facts from written interpretation, stating its own uncertainty, and bounding every answer so it fits a limited context window. You can enter it from the dashboard, from the command line, or as a connected coding agent; all three read the same memory.

| Capability | What you get | Why it matters | Maturity |

| Responsibility map: areas → subsystems → files | A small number of named architecture areas, their subsystems, and every eligible file placed exactly once — each group carrying its responsibility, why those files belong together, supporting and contradicting evidence, and a confidence rating | Grouping is by responsibility, not by folder. ### Nuance worth knowing

**Bounds are real, and they are the point.** The goal-scoped briefing is held to a size budget (about 20 KB by default, configurable) and a cap on related files (25 by default). When material does not fit, detail is compacted; in the worst case only the route and matched names survive. Any single connection view returns at most a set number of files and links, and walks at most three steps outward; a file with unusually many neighbours has some left out, and the view says how many. A tight budget genuinely removes nuance — the answer says so.

**Written explanations exist per file, per group, and for the repository as a whole** — not per function or class. Symbol matching is by name, signature and the file's written description; a goal returns at most a handful of matched symbols, or none plus the file itself, rather than inventing a match.

**Search is word-based** over both code text and written meaning. There is no synonym or learned-similarity matching, so a concept expressed in entirely different vocabulary can still be missed. Results are capped (20 by default, 50 maximum). Before the written map is built, only paths, names and coarse summaries are searchable.

**Reachability counts are a floor, not a guarantee.** Runtime registration, framework wiring, names built while running, generated code, configuration and shallowly-read languages can connect code invisibly. Indirect dependants are possible follow-on effects, not a list of files that must change.

**The responsibility map is deliberately capped** — roughly six areas and up to thirty subsystems by default — so a genuinely sprawling repository is compressed into that shape, with excess groups merged into the closest retained responsibility rather than kept separate. The map is not allowed to dump hard cases into a generic bucket. One exception is disclosed honestly: pinning files to specific groups can push the map past its size limit, and the displaced remainder is then collected into a general group whose assignments are explicitly marked low-confidence for exactly that reason. There is no human approval gate — the map finalises itself after its automated review passes. Hints and fixed placements are available; nobody signs off.

**The export is a bounded summary, not a complete copy.** Very large repositories will have items omitted, with counts, rather than producing an unbounded file. Working through a very large record means paging in the interface rather than exporting it whole.

## Area 2 — Attention: what to look at first

Everything the tool observes could be reported. Almost none of it should be. AnaxiGraph produces a short, ranked queue of things genuinely worth looking at, backed by a complete record that is never pruned to keep a screen calm. Every entry is written as an argument a reader can check: what was seen, why it may matter, when the code is probably fine as it is, the smallest sensible next step, and how a later scan will show whether it worked. Nothing here is a verdict.

| Capability | What you get | Why it matters | Maturity |
|---|---|---|---|
| Bounded attention queue | "Findings to check first": at most about twenty items, most-useful-first, each already qualified. The same short view reaches a connected agent and `anaxigraph review` | A checker that dumps thousands of hits teaches everyone to ignore it. A capped queue is short enough to read to the end, and it hides rather than deletes — every view states the true total | Shipped |
| Complete record beside the queue | Every saved observation, with filters, paging, and totals broken down by level, by check and by state, plus what each page left out | Tools that quiet their interface by discarding low-severity results destroy the ability to ask "has it always been like that?" later | Shipped |
| A finding as an argument, not an alert | What was seen as measured facts; why it could make the code harder to understand, test or change; when the current design may be perfectly reasonable; the smallest sensible next action; how focused tests plus a later scan will check the result | A rule code, a path and a line number makes every reader reconstruct the reasoning, and most readers skip it. Because each finding argues against itself, a reader — or an agent — can decline it on stated grounds | Shipped |
| What a change would touch | The affected files, their architecture areas, the names other code can call in them, which affected paths are tests, and how far a change could reach | Turns "this file is too big" into a piece of work whose size can be judged before starting | Shipped |
| Ranking with the reasons written out | Order decided by the project's own rule about the condition's level, how directly it was observed, how connected the affected files are, how many files are involved, and whether the condition previously disappeared and returned — each listed as a sentence. A 0–100 number is shown, explicitly labelled sort order only | An unexplained priority number can only be accepted or ignored; stated reasons can be argued with, which is what makes a queue usable by a team | Shipped |
| Fact, interpretation and recommendation kept apart | Each finding says whether it was counted or traced directly from repository data, or suggested by an AI reading written descriptions — and explains what its confidence figure means. AI-sourced suggestions that no directly observed finding corroborates are shown as held back, with the reason | "The AI thinks your code is bad" is unfalsifiable; once a team notices, everything the tool says loses credibility | Shipped |
| No score, no mandate | No health grade, letter or index. Sorting numbers are labelled as sorting numbers. A finding never authorises an edit. Possible unused code is never declared safe to remove | A single quality number gets optimised, then pasted into a status deck, and within a quarter it measures nothing. The same discipline protects agents, which otherwise treat any surfaced warning as an instruction | Shipped |
| Lifecycle you drive | From the dashboard or `anaxigraph finding`, mark an item reviewed, planned for agent work, accepted as a known risk, or not actionable; reopen an accepted or dismissed one. Decisions survive rescans | Accepting a risk once does not mean re-triaging it every week, and a condition that returns after being fixed comes back labelled as a regression rather than as a fresh discovery | Shipped |
| When a problem appeared, and whether it came back | Across the saved states retained for the repository: first visible here, gone by there, returned by then, or present since the earliest retained state — with the answer stating its own precision | Age changes the decision completely. Something introduced by last week's feature is worth stopping for; something present since the first commit is a planning item. Most tools present both identically | Shipped |
| Filters, grouping and honest counts | Narrow by view, state, level, which check produced it, architecture area, strength of evidence, and text in the path. Repeated observations of the same check in the same area are grouped with counts | Forty instances of one shape in one area is a single design conversation, not forty tickets. Filters change presentation only — reported totals always describe the underlying record | Shipped |
| Findings sized to an agent's context | A connected agent can request findings under an explicit token budget, receive the same plain-language content compactly, see exact counts of what the budget displaced, ask for only the work already planned, and pick the list up where it stopped | Most integrations force a choice between a truncated list the agent believes is complete and a full list that eats its window | Shipped |
| From a finding to planned agent work | "Plan agent work" records the finding as selected and produces a handoff: the goal, the files worth reading, the relevant tests, files marked for extra care, an overall risk level, verification steps, this finding's history, and a ready-to-paste prompt | The person and the agent work from one explanation, so the handoff cannot drift. Because planning is a deliberate act, an agent can distinguish work someone asked for from observations it merely happened to see | Shipped |
| The project's own rules define what counts as a problem | Thresholds for file size, function length, branching, how many files one file may use or be used by; forbidden dependencies between named areas; drift from a declared area; a coverage floor; a conservative unused-code rule. Rules can be scoped to paths, given their own level, or switched off. Findings quote the project's own rule in their wording | Universal thresholds are wrong for somebody in every repository, and arguing with a vendor's default is unwinnable. This moves every disagreement to the rule, where it can be settled once and written down | Shipped |
| Deliberately conservative possible-unused-code | A candidate appears only when links resolve cleanly enough overall, nothing indexed points at it, history shows it untouched for a configured period, and no entry point or startup registration was detected — listing the checks it passed and the checks a human still must perform | Absence of a visible link is not evidence of absence, and dead-code tools that forget this cause outages. The check disables itself when link evidence is too ambiguous, and says that it did | Shipped |
| Attention delivered inside the change | When you ask where a change belongs, existing findings on the files that change is likely to touch travel with the answer, re-ranked for that task and capped at a handful | Attention arriving at the moment of decision changes the decision; the same information in a report nobody opens changes nothing | Shipped |
| One wording everywhere, no jargon drawer | The same sentences on screen, in `anaxigraph review`, in what an agent receives, in the change-planning answer, and in the copied prompt. Specialist vocabulary is expanded in place; identifiers and scores carry an adjacent plain sentence | When the interface and the programmatic surface tell different stories, people stop trusting both. Pushing jargon into a collapsed panel is explicitly rejected as a way of pretending something was explained | Shipped |
| Depth of findings outside Python | The deepest reading — precise structure, function boundaries, branching, resolved links — is available for Python. JavaScript and TypeScript get a lighter reading; other recognised formats are handled heuristically or catalogued. Each analyser declares what it can and cannot see, and those limits travel with the evidence | Producing weaker findings that look identical to strong ones is how a tool loses a team's trust permanently | **Partial** |

### Nuance worth knowing

**Two of the ranking inputs are not present on day one.** Change-frequency reasons require the background history import to finish; coverage reasons require a coverage report you produced and pointed the tool at. Until then the ordering is real but thinner — essentially the rule's level, how directly the condition was observed, and how connected and numerous the affected files are. The reasons listed on each item show which inputs were available.

**Resolution is normally proved, not asserted — with one honest qualification.** In the dashboard, *resolved* and *returned* are not buttons: a later scan that no longer observes the condition marks it resolved, and a scan that observes it again marks it returned. That is the path the interface enforces, and it is why the record cannot simply be tidied into looking healthy. A person working from the command line can still set those states by hand, so this is a property of how the product is designed to be used rather than something the tool makes impossible. Separately, a finding can retire without any code change — the file was deleted, moved outside the included paths, or a threshold was loosened — so "resolved" means "no longer observable", not "fixed".

**Setting a state is a human action.** A connected agent can read findings, see which were planned, and take a handoff; it does not change states itself. Dismissing hides an item from the attention view rather than deleting it.

**Budget floors differ by route.** There is a floor and a ceiling on the token budget for agent-facing findings. Asking the service directly for less than the floor is refused rather than quietly honoured; asking through the coding-agent connection for less than the floor gets you the floor. If even one result cannot fit the budget, the answer says so rather than returning an empty page that would read as "nothing to report".

**When the ordering rule itself changes**, that is announced as a deliberate change to how the product behaves, so a reshuffled queue is never a mysterious morning surprise. The same applies to the wording of an explanation: changing what a finding says is a deliberate, tested product change, not incidental copy editing.

**The checks are structural.** They do not assess correctness, security, performance, or whether the software does the right thing. Coverage-based findings require an imported report; a missing report is reported as *no report*, never as measured zero. Pages of the complete record are capped at a couple of hundred items at a time.

## Area 3 — Architecture guidance

The same saved understanding is turned into design advice: where new work belongs, which files are quietly doing the same job, which boundaries have eroded, which code may no longer be used, whether a bloated file contains a real seam, and which of 128 named patterns and failure modes actually fit the code in front of you. Every recommendation leads with what was observed, why it may matter, the smallest sensible action, reasons the code may be fine as it is, and how to check the result. Pattern judgements are re-checked by a separate AI pass before they can be shown.

| Capability | What you get | Why it matters | Maturity |
|---|---|---|---|
| Design decision for a stated goal | Where the change belongs, what already does something similar, which extension points exist, which caller-facing contracts must stay true, the risks, the focused tests, and a route from area to subsystem to file to matching functions — carrying consolidation, unused-code, decomposition and pattern advice for that same working set | The design guidance and the working set are never two different pictures, and the answer says up front how much of it rests on machine-read facts versus written interpretation | Shipped |
| Repeated responsibility and consolidation advice | Merge, split, keep separate, or needs review — naming the specific overlapping files, what was observed, why it may matter, what to do, reasons to be careful, and how to check | Duplicate-code detectors compare text and leave the judgement to you. This states the design conclusion, treats "keep these separate" as a first-class outcome, and is required to carry contrary evidence alongside supporting evidence | Shipped |
| Boundary erosion and area drift | Two distinct reports: a file whose declared home no longer matches how it behaves (with both the declared area and the area its paths and links suggest), and a dependency that crosses a boundary the team declared off-limits (with both files named and the smallest way to reverse it) | A dependency linter can say an import is banned but has no opinion on whether a file quietly changed jobs. This names the disagreement between intended and observed design and asks you to resolve it | Shipped |
| Architecture policy a team defines | Maximum lines per file and per function, a ceiling on decision branches, ceilings on how many files one file uses or is used by, no dependency cycles, no dependency between named areas or paths, no drift from a declared area, a coverage floor, and a conservative unused-code rule — each scopable to paths and given a severity | One rule definition feeds the dashboard, the command line, and what a coding agent receives, all in identical wording, so an architecture document becomes something checked rather than aspirational | Shipped |
| Conservative unused-code candidates | Candidates that open by saying they are not permission to delete, explaining what was checked, the specific blind spots of static analysis, and the checks to run before removing anything | Most unused-code tooling is confidently wrong about framework wiring, configuration-driven loading and reflection, and quietly teaches people to distrust it | Shipped |
| Large-file decomposition map | For a file at or near its size limit: up to five proposed responsibility slices with the symbols and single job that belong together, which existing file or area each should move into, the contracts that must stay stable, a safe extraction order, focused tests, and the evidence arguing against splitting at all | Size alone never produces a split here. A concrete split appears only when at least two separate responsibilities are named with both supporting and opposing evidence; otherwise you are told to keep it together, which is a real answer | Shipped |
| Design pattern catalog | 128 named entries across eight equal families — function construction, object and interface design, data and state, module boundaries, composition and workflow, integration and concurrency, reliability and testing, subsystem architecture — deliberately including failure modes as well as constructive patterns, each with intent, benefits, liabilities, migration cautions, what must remain true afterwards, references, and its relationships to other entries | The standard being applied is a readable catalog you can inspect and argue with, not an opaque prompt. Because conflicts and alternatives are declared, results can say "this competes with that" instead of recommending two incompatible things at once | Shipped |
| What a pattern evaluation tells you | Present, partial, absent or uncertain; a suggested action; what was seen; why it may matter; the smallest sensible action; explicit reasons not to change the code; how to verify; and what the pattern's name means in plain words. Nine distinct 0–100 answers presented as five questions, each with its meaning stated beside it | Counter-evidence is a required part of the answer, so the result can talk you out of a refactor. A high change-cost answer means more work, not a better outcome — and the tool says so rather than leaving you to guess | Shipped |
| Ask in both directions | Name a file, class, function, subsystem, area or the whole repository and get its best-fitting, already-present, conflicting and highest-opportunity patterns — or name one pattern and get its strongest examples, weak conformers, and where introducing it would help. Filter, order, page, and opt into detailed evidence (`anaxigraph patterns`, the Patterns screen, and the agent connection) | One bounded query in either direction, identical wording for a person and an agent, and reading results never triggers a fresh scan | Shipped |
| Why this code was or wasn't checked | For one named pattern, which pieces of code were chosen for evaluation and which were skipped, each with one explicit reason: no positive evidence, contrary evidence present, below the priority threshold, displaced by the bounded plan, or the plan is not ready | Pattern evaluation is necessarily sampled. The honest response is to make the sampling auditable, so an absent result reads as "not examined, and here is why" rather than "nothing wrong here" | Shipped |
| Independent review of its own pattern judgements | Every judgement is checked by a separate AI pass before it can be shown. The reviewer may agree, correct the result and return the corrected version, or record that another reading is equally supported and keep both visible — checking specifically for the wrong target, a misidentified pattern, an overlooked alternative, ignored counter-evidence, contradictory ratings, needless machinery, and thin evidence | A first judgement cannot reach you unreviewed, a correction is recorded as a correction, and genuine disagreement is preserved rather than smoothed into a confident single answer | Shipped |
| Extend the catalog for your own conventions | The catalog is written as content rather than code: a house pattern is authored the same way the shipped ones are — name, family, what makes it relevant, evidence for and against, benefits, costs, and what must stay true afterwards — and can be validated against the same rules today | Authoring a pattern is writing, not programming. An entry that asks for evidence the tool has no way to gather is rejected the moment you add it, with the reason, instead of quietly never matching anything | **Intended** |

### Nuance worth knowing

**Extending the catalog is not yet a running capability.** A custom set can be authored and checked for well-formedness today, but the running product evaluates against the catalog it ships with; there is no way to point evaluation at a catalog you wrote. Until that lands, the shipped 128 is the vocabulary you get. When it does land, entries will still be unable to make the tool read code it could not already read, invent their own way of inspecting source, or behave differently for one programming language — and the catalog will keep an overall size ceiling.

**Pattern coverage is sparse on purpose.** By default at most four patterns are evaluated per piece of code and around two hundred evaluations per repository map, with reserves that spread coverage across sizes of code and across patterns. Absence of a pattern result is not evidence of absence of a problem. The order in which candidates were worked through is labelled as exactly that — the order work was done in, not a rating and not advice to refactor. Twenty results are returned per query by default, one hundred at most, and only evaluations that completed their independent review appear.

**The independent review is a second AI pass, not an independent vendor.** In normal use it is the same connected agent and model configuration, so it catches inconsistency and overreach better than it catches a shared blind spot. It consumes model budget on top of the first pass. There is deliberately no human approval gate.

**Unused-code candidates require several gates to agree**: no resolved or ambiguous inbound link at all, trustworthy link resolution across the repository, code reading deep enough to recognise entry points and registrations with none found, and a configurable minimum age since last change (90 days by default). Configured, conventional and detected entry points are suppressed. An AI-suggested candidate only surfaces when a structural candidate at the same granularity corroborates it, so a whole-file candidate can never vouch for a single function. The check is suppressed entirely for languages read only heuristically. Runtime-only wiring is a permanent blind spot.

**The rule kinds are deliberately fixed.** A general policy language is an explicit non-goal, so a rule the current kinds cannot express is not expressible.

**Decomposition and consolidation both need current written descriptions** of the files involved; without them, the answer degrades to structural facts and says so. Decomposition returns at most five files, five slices per file and thirty symbols per slice. Where no honest destination can be justified from existing code, the destination is left blank and you are told to check the map before creating a new sibling file.

## Area 4 — Building and keeping the understanding

The written layer — file explanations, the responsibility map, the whole-repository account, pattern judgements — is produced by the coding agent you already work with, spending its own context and tokens on bounded, one-piece-at-a-time evidence. The results are checked and kept beside the repository, not inside it, so the next session inherits them instead of rediscovering the system.

| Capability | What you get | Why it matters | Maturity |
|---|---|---|---|
| Written description of every file | What it does, its role, the jobs it owns, files with related or overlapping work, the places designed for adding behaviour, where related work belongs, patterns that may fit, code that may no longer be used, and the risks the writer saw — with an evidence-strength rating whose meaning is stated, and who wrote it | The reading is done once, written in sentences a newcomer and an agent can both act on, with an explicit "not recorded" rather than invented filler where the writer had nothing to say | Shipped |
| Whole-repository explanation | What this repository does, the role it plays, where new repository-wide work belongs, patterns that may fit at that scale, possible unused code, and repository-wide risks | Synthesised from the per-file understanding and the responsibility map rather than from a fresh skim of the top-level folders | Shipped |
| The connected agent writes it, on its own tokens | With agent-funded mapping enabled the tool needs no model key and no model account of its own. It works through the repository one file or code area at a time, gives the agent only that slice to read, requires an answer in the form it asked for, checks it before keeping it, and records which coding agent and model wrote it | The cost lands where you already have a subscription and an authenticated agent, the agent never sees the whole repository at once, and a malformed answer is retried rather than kept | Shipped |
| Durable build you can start and walk away from | One command (`anaxigraph understand . --executor codex --background`, or the Claude equivalent) runs the whole build in the background, surviving the session that launched it. `anaxigraph semantic-status .` reports whether the build is still going, when it last made progress, where to read its output, which repository's memory it is updating, how far it has got, what failed, what remains, and the exact command that picks it up again | It separates "something is alive" from "work is progressing" from "the queue is empty", so a run cannot report success while tasks remain, and an abandoned run is shown as idle-but-resumable rather than as a phantom job | Shipped |
| Understanding persists across sessions | Everything written stays available to a new agent session, a different agent, or a person in the dashboard. Unchanged code reuses its existing description; switching model, executor or reasoning effort changes only the recorded provenance, never freshness | The difference between a tool that summarises on demand and one that has a memory. Changing your agent setup does not silently invalidate a repository's worth of paid work | Shipped |
| Staying current when code changes | Only what actually went out of date is rewritten: files whose code changed, files never described or that failed last time, and files whose neighbours changed in a way that alters what the file works against. Untouched code is not re-read | Two failure modes are ruled out by design: silently presenting an old map as current, and dropping to a misleading zero-knowledge state when something changes. Stale understanding stays visible and is labelled stale | Shipped |
| Ask by meaning instead of by filename | Search and goal-scoping match against written responsibilities as well as code structure, so a goal phrased in concepts reaches the responsible code without you knowing its filename, and results name the area and subsystem it sits under | Name-based search only works when you already know the vocabulary the original author used | Shipped |
| Placement guidance: extend this, or create something new | The preferred place, the existing responsibility that should absorb the work, the specific extension points, local precedents to copy, contracts that must keep holding, the tests most likely to matter, the risks — and an explicit statement when there is genuinely no honest home and a new sibling is warranted | This is the decision that produces file sprawl when an agent gets it wrong. Answering it from written responsibilities rather than path similarity points at the module that already owns the job | Shipped |
| Consolidation and possible-unused notes that refuse to overclaim | Each stated as conclusion, what was observed, why it may matter, what to do, what would make the suggestion wrong, and how to check. Every unused-code candidate starts from "do not delete yet" and names the blind spots | An AI hunch about dead code cannot become a deletion order: it is suppressed unless rule-based evidence at the same granularity agrees | Shipped |
| Honest uncertainty on every written claim | An evidence-strength value with an adjacent sentence saying what it means and what it does not prove, plus who and what produced it — in the same wording in the dashboard, on the command line, and in everything handed to an agent | There is no separate technical-details drawer where unexplained labels hide. If a statement needs a specialist word, the word is defined in the same sentence | Shipped |
| Budget, privacy and cost visibility | Written mapping is off until deliberately enabled. What may be sent is controlled by include/exclude rules over paths; work is bounded by a per-run task cap, a cap on concurrent model calls, per-task time limits, and an optional daily spend ceiling. Afterwards, status reports model names, completions, failures, task time, input and output tokens and cost, for the current run and lifetime | The path exclusions are a source-egress control, not just scheduling. A call whose usage was never reported is shown as unknown usage — zero is never presented as proof a call was free | Shipped |
| What is machine-verified about the understanding | That every file the settings include is either described, deliberately excluded, or visibly listed as failed — never silently absent; that every included file appears in exactly one smaller group; that omitted files are repaired back into visibility; that excess groups merge into the nearest real responsibility instead of a generic overflow; that a submitted answer matches the required form before it is kept; that an assessment cannot surface as a recommendation before its critique; and that an interrupted build restarts and finishes with nothing outstanding | These are the failures that quietly destroy trust in an AI-written map — silent gaps, unclaimed files, a catch-all absorbing the hard cases, a run that stops early and reports success. They are checked by rules, so they hold regardless of which agent wrote the content | Shipped |
| Evidence that it works at repository scale | A full live run on this tool's own repository; a rule-based planning exercise at 2,000 modules; and a repeatable 200-file exercise in which the build is killed partway through, the tool is fully shut down and started again, and it picks the abandoned work back up and finishes it — without a single write to the analysed source | The deterministic evidence and the paid live evidence are stated as what they each are, not blurred together | **Partial** |

### Nuance worth knowing — read this before planning a rollout

**What a first build actually costs.** On this tool's own repository — roughly 470 files — a complete build cost about 12.5 million input tokens and about 900,000 output tokens. It finished in about 45 minutes with 30 model calls running at once, which is a deliberately raised setting: **the shipped default runs one model call at a time and takes correspondingly far longer.** Token cost is roughly proportional to repository size; elapsed time depends entirely on how much concurrency you allow and what your agent plan tolerates.

**That cost lands on your coding agent's own plan.** "No model key required" means the reasoning is charged to the subscription your agent already uses and counts against its usage limits. A figure like twelve million input tokens will consume a meaningful share of an ordinary plan's allowance, and while the build runs, that headroom is not available for your own work. A build interrupted by a plan limit resumes rather than restarting.

**The demonstrated quality evidence is narrow.** One full live run, on this tool's own repository, roughly 470 files, written by its own author, with one model family at one reasoning setting. The planned paid run against an unrelated external repository of about 1,900 modules is deliberately paused and has not happened. There is no scored accuracy benchmark for the written understanding; usefulness is judged by whether real coding goals reached the right code, recorded as prose rather than as a number. The *mechanisms* — completeness, unique placement, resumability, answer shape, independent review before publication — are checked by rules and hold regardless of which agent writes the content. The *quality of the prose* rests on that single self-hosted repository. Behaviour on someone else's large repository, with a different model, over a codebase nobody involved already understands, is unproven. Treat large-codebase use as an evaluation you would be running, not a claim being made.

**Refresh is deliberately not automatic at the written layer.** Ordinary saves do not trigger model work; the written layer lags until you ask for a refresh at a coherent checkpoint. That is a cost decision. A repeated refresh of an unchanged repository creates no model work at all, so keeping the map alive is cheap even though building it was not. An agent making a decision that truly needs a fully current written map should wait for the map to report ready rather than assume it.

**Understanding written by a model you have since replaced stays in place** until the underlying code changes or you deliberately force a reread. The memory is per-repository.

**Nothing the tool produces is written into your repository.** The understanding lives beside it, so it can be kept, copied or thrown away without touching a single tracked file, and a clean checkout stays clean. The one thing that does land in the repository is the settings file you choose to create and commit.

**Running the connected agent through tasks one at a time inside a chat session works but is a fallback**, not the way to build a whole repository — the durable background command is.

### Nuance worth knowing

**There is no automatic poller in the simple local start.** `anaxigraph up` builds the map when it starts and refreshes it on request — from the dashboard, or by a connected coding agent where the operator has allowed that. Continuous polling is what the packaged isolated setup runs, and it can also be started on its own. A project can additionally opt in to refreshing the written explanations on every scan or watcher pass rather than only when asked.

**There is no shipped build gate.** Reviewing findings from the command line always succeeds regardless of what it finds; there is no supplied command, action or exit signal that fails a build on new or worsened findings. Wiring one is possible — every command can emit machine-readable output, and the review can be narrowed to only what is new since the last scan or only what has resolved, so a team can compare against their own recorded baseline and decide what should fail. **The pass/fail decision is yours to build; the product ships the evidence, not the gate.**

## Area 6 — Containment, data handling and trust

| Capability | What you get | Maturity |
|---|---|---|
| Read-only toward your source, always | The tool observes the repository and never edits, deletes, moves or executes anything in it. Every recommendation is a proposal, and the tool says so in the recommendation itself | Shipped |
| Containment when run in the packaged way | Your repository is mounted read-only, all of the tool's own state is kept outside your repository, it runs with reduced privileges, it publishes only to your own machine by default, and it can be restricted to accept requests only under a named address | Shipped |
| Agent-triggered work is a granted permission | Whether a connected coding agent may trigger a refresh at all is the operator's decision — on in the simple local start, off in the packaged isolated setup, where a background refresher does that job instead | Shipped |
| Credentials never written into agent configuration | Credentials or URL fragments are refused rather than written into your coding agent's connection entry | Shipped |
| Egress control over what may be sent to a model | Include and exclude rules over paths decide what can be handed to the model when the written understanding is built | Shipped |
| Provenance on every written claim | Each written explanation records which coding agent and model produced it, how many neighbouring files it was weighed against, and how confident it is | Shipped |

### Nuance worth knowing — read before the first build in an organisation

**Building the written understanding sends repository source to whichever model your connected agent uses, under that agent's own terms.** The exclusion rules are the control for this, and the out-of-the-box exclusion covers vendored and generated paths only — meaning settings files, fixtures and anything containing credentials are eligible by default. There is no secret detection. If your organisation needs egress restricted to an approved subset, write those exclusions **before** the first build; this is the one decision that cannot be undone afterwards.

**The service has no accounts, no login and no per-repository permissions.** Anything that can reach the endpoint gets everything it exposes. It runs as a companion service on your own machine, reachable only from that machine or through a secure tunnel you set up. It is not a shared multi-user server.

**"Shared understanding" means one person and their agent, on one machine.** The understanding is built and held per developer machine, or per container beside one checkout. Two engineers do not automatically share one accumulated understanding; each build costs its own tokens and hours, and two builds of the same repository can differ. The backup and restore path is the way to move one built understanding to another machine rather than paying for it twice. **If you are sizing this for a team of forty, size it accordingly.**

**A wrong written description is durable.** It is AI-written, it can be wrong, and because it is only refreshed when the underlying code changes, an incorrect explanation persists across sessions and quietly influences future placement decisions. Every explanation carries its evidence strength, its confidence and the agent and model that wrote it, so a suspect one can be identified; the remedy is to force a reread of that code, or to constrain the map with hints and fixed placements. Anything that can reach the local endpoint can contribute to that memory.

## Limits and boundaries

### Language depth — **Partial**, and the most important limit here

| Language | Reading depth | What that means for answers |
|---|---|---|
| Python | Deep | Real structure, function boundaries, branching, named parts, resolved links between files. All capabilities apply at full strength |
| JavaScript / TypeScript | Lexical | Weaker symbol and relationship evidence; dependency, placement and unused-code answers are correspondingly weaker |
| Other recognised source and text formats | Heuristic or inventory-level | Little more than presence and coarse grouping. Unused-code detection is suppressed entirely |

Every fact records which depth of reading produced it, and the repository summary reports the mix, so you can calibrate rather than trust uniformly. **Recognising a file extension is never counted as supporting a language.** Parser-backed support for JavaScript/TypeScript, Go, Rust and Java is named as a possible next language step, not committed work.

### Platforms and environments

| Environment | Status |
|---|---|
| Linux x86-64, container or local install | Supported and release-gated |
| Linux ARM64 | Best effort — the image is published, but no native runtime is exercised on every release |
| macOS (Apple silicon or Intel), via containers | Best effort; the recommended macOS path |
| macOS, local install | Best effort — install and startup are release-gated; serving, watching and browser behaviour are not |
| Windows via the Linux subsystem | Best effort. Keep repositories on the Linux side of the filesystem for usable performance |
| Native Windows | **Not supported.** Use the Linux subsystem instead |

"Best effort" means not known to be broken, only not release-blocking. Dashboard interaction is verified in one browser engine; the others are best effort. The dashboard is served locally, so a browser on another machine should reach it through a port forward.

### Prerequisites

The target must be an ordinary Git working tree readable by the tool — without Git there is no history evidence and no product. You need either a recent Python toolchain or a container runtime. The packaged container deliberately bundles no coding CLI and accepts no hosted-model key, so the agent that writes the understanding has to run on an authenticated machine.

### What not to expect

- **No before-and-after verdict.** After a change you refresh and read the evidence separately: findings that resolved, findings that are new since the last scan, findings that returned after having been fixed, what differs between two saved states, measurements recorded for each retained state, and the same goal re-asked against the refreshed understanding. There is **no saved before-change snapshot you carry between asks**, and **no single composed answer** classifying each effect as introduced, worsened, improved, resolved or pre-existing. That composed capability is Intended, not shipped.
- **No health score, grade or index.** Anyone who needs a single number to report upward must define it themselves from the exported record, and should expect no support for defending it.
- **No automatic fixing.** No auto-fix, no bulk remediation, no button that marks a condition resolved.
- **No correctness, security or performance analysis.** The checks are structural.
- **No coverage measurement.** Coverage is imported from reports your own pipeline produces, and imported figures are only as fresh as the last import — a months-old report will keep influencing the queue's ordering as though it were current.
- **No proof of scale on unfamiliar codebases.** Everything demonstrated end to end has been demonstrated at roughly 470 files, on this tool's own repository, by its author. Structural handling has been exercised against larger synthetic material; a written understanding of a large, unfamiliar repository has not been produced or measured.
- **Runtime wiring is a permanent blind spot.** Framework registration, reflection, configuration-driven loading, generated code and dynamic name construction cannot be seen by reading source. The tool discloses this rather than measuring it, and never treats a missing link as proof that code is unused.

## Intended direction

Four things the product wants to become. None of them is available today.

**1. One shared, plain-language consequence after each refresh.** After a coherent edit or commit, both the dashboard and the coding agent receive the same short explanation of what changed — the observed change, its architectural consequence, the recommendation and its confidence, the reasons to leave things alone, and the smallest safe follow-up with its verification step. The pieces exist: incremental refresh, findings that appear, resolve and return, differences between saved states, and plain-language explanations. What is outstanding is converging them into one automatic post-edit consequence delivered to both audiences at once. Even when complete, a changed measurement will remain evidence of direction, never proof that the design improved: the intended outcome and focused tests still decide.

**2. One continuous journey from program purpose down to a symbol.** A single guided path from what the program is for, down through one user-facing capability, to areas, subsystems, files, symbols and the code that implements it — keeping the selected concept selected while you switch between list, connection and history views, with ordinary-language consequences first and the exact evidence one click away. Today you can reach every one of those levels, but you move between the Overview, Files, Graph and History views to do it, and the selected concept does not always carry across. The goal is that a newcomer or a non-programmer can trace a feature to its code unaided.

**3. A deliberately small default surface.** The stated target is about five task-centred journeys for a person and no more than ten obvious actions for a coding agent, with low-level and operator controls reachable but off the normal path. **Currently Partial:** a person still meets more top-level destinations, and an agent still sees more available actions, than that ceiling. The reduction is being done one consolidation at a time, without losing tested behaviour and without hiding complexity behind a new layer. The point is reliability with everyday agents: a workflow an unremarkable agent follows correctly on the first try is worth more than a rich toolbox only a frontier model sequences properly.

**4. Pointing the running product at your own pattern catalog.** Authoring and validating a house catalog works today; making the running evaluation use it does not.

## Deliberate non-goals

These are parked, not queued. Each reopens only if concrete user evidence shows it materially improves the core understanding-and-change loop.

| Non-goal | Why it is parked | What would reopen it |
|---|---|---|
| Broad parser-backed coverage of many more languages | A tool that understands one kind of repository deeply and runs reliably beats one that recognises everything shallowly. Breadth would dilute exactly the guarantees — resolved relationships, honest confidence, bounded answers — that make current answers usable | Evidence that the core loop is excellent and that a specific language is the binding constraint on real users. This is a scope decision, not a technical barrier |
| Adapters for non-code assets — schemas, infrastructure definitions, documents, tickets | Breadth of artefact type multiplies the surface while diluting the one thing the product is trying to be excellent at | Evidence that architecture decisions in the code cannot be made well without them. Today, coupling between code and those artefacts is invisible: a change safe in the code but breaking a schema or a deployment will not appear |
| A general third-party plugin ecosystem | Every added extension surface is paid for later in confusion and maintenance. Catalog content is extensible; the tool's reading ability is not | Sustained demand that cannot be met by catalog content alone |
| Rich-media understanding — images, PDFs, audio, video | Not on the path from "understand this repository" to "make this change fit" | Nothing currently foreseen |
| A repository health score or hotspot leaderboard | A single quality number gets optimised, then used to compare teams, and stops measuring anything. It would also undermine the separation of measurement from judgement the rest of the product depends on | Nothing. The attention queue plus appeared/resolved/returned history answers the useful version of the question |
| Automatic fixing, refactoring, merging, splitting or deletion | The value on offer is judgement about architecture, which depends on the tool being a trustworthy independent observer. A tool that both raises the finding and closes it has no independent check left, and "the warning went away" stops being evidence of anything | Nothing. Keeping editing on the agent's side means the change goes through normal review and tests |
| Learned-similarity search, or a second parallel model of the code | One inspectable model whose every claim traces to evidence beats two that can quietly disagree. Similarity scores are hard to audit and would blur the deliberate line between facts, interpretations and recommendations | Evidence that word-based matching over code and written responsibilities misses goals the goal-scoped briefing also cannot recover |
| A general architecture-policy language | The fixed rule kinds keep findings explainable in ordinary sentences and keep the queue small | Repeated, concrete rules real teams need that the existing kinds genuinely cannot express |
| Extra dashboards, generic operations tooling, website, demo and ecosystem promotion | Presentation work is not allowed to starve the core change loop | Nothing on the current roadmap |

**The admission test.** Before anything is built it must state which of the three promises it strengthens, which concrete human or agent decision it makes easier, which existing evidence it reuses, which existing surface delivers it, what it removes or replaces, the smallest end-to-end proof that it works, and what new machinery it avoids. Anything that cannot answer all of that is optional and does not block the roadmap. This is a judgement gate applied in review, not an automated check, and it is intentionally conservative: it keeps out work some users would genuinely want, on the grounds that the core loop must be excellent before the product gets wider.

## Why this product is good at what it does

Six arguments, each of which is a decision that could have gone the other way.

**1. It answers the question before the change, not after it.** Most architecture tooling arrives as an audit — a report written about a decision that was already made. The highest-leverage moment is earlier: when an agent or a person is deciding *where this goes*. That is the moment an isolated prompt guesses from whatever few files are in its context and creates a plausible new file next to the one that should have been extended. Grounding that single decision in the repository that actually exists is the difference between a fast agent that fits the system and a fast agent that sprawls it — and it is the reason the goal-scoped briefing, not the dashboard, is the centre of the product.

**2. One understanding, two front doors — not two products.** The easy build is a human product and an agent product that each interpret the repository their own way, and then a human and an agent disagreeing with no way to tell which one is stale. Because both draw on the same memory and receive the same sentences with the same evidence and the same stated confidence, the handoff between a person and an agent is a continuation rather than a translation. This is also why the wording is treated as part of what the product promises rather than as copy.

**3. Every answer argues against itself.** Advice without counter-evidence is a dare. Consolidation results treat "keep these separate" as a first-class outcome. Decomposition returns "keep it together" as a real answer. Pattern evaluations are required to carry reasons not to change the code and are re-checked by an independent pass that specifically looks for needless machinery. Findings state when the current design may be perfectly reasonable. Putting the reasons to leave the code alone beside the reasons to change it is what lets a person or an agent decline deliberately — which is precisely what makes the suggestions worth reading at all.

**4. It refuses the moves that would make it look better and be worse.** No health score, because a score gets optimised and then measures nothing. No auto-fix, because a tool that raises and closes its own findings has no independent check left. No deletion of evidence to keep a screen calm, because that destroys the ability to ask "has it always been like that?". No language-support claim from a file extension. No confident dead-code verdict where wiring is invisible. Each refusal costs convenience — there is no number for a status page, no cleanup button, and some answers end in "this cannot be determined by reading the code". Naming them as refusals is what makes them something you can rely on.

**5. It separates completeness from truth, and says which it has proved.** Completeness, unique placement, resumability and answer shape are checked by rules and hold no matter which agent writes the content: every included file is described, excluded, or visibly failed; no catch-all absorbs the hard cases; an interrupted build restarts and finishes empty; an assessment cannot surface as a recommendation before its critique. None of that validates truth — a description can be complete, well-shaped, uniquely assigned and wrong. The tool states that distinction rather than letting the rule-checked half vouch for the other. Stating the evidence base for the written prose honestly, including the fact that it is one self-hosted repository, is part of the same discipline.

**6. It fits inside an agent's budget by construction.** Every read is size-limited and paged, states its true total and what it left out, and defaults to the smallest useful answer. The goal-scoped briefing degrades by compacting optional detail while preserving the placement conclusion and the constraints. An empty page is never returned where "nothing fits the budget" is the truth. Omission is reported rather than silent — the difference between a briefing and a truncated file read, and the difference between an agent that knows it is looking at a fraction and one that acts as though it saw everything.

**And one honest counterweight.** The mechanisms above are real and checkable. The demonstrated quality of the written understanding rests on a single repository of roughly 470 files, written by the tool's own author, with one model configuration. The product's claims about mechanism should be taken at face value; its claims about your codebase should be treated as an evaluation you would be running.
