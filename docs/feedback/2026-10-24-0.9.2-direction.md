# Maintainer direction for AnaxiGraph 0.9.2

**Date:** 24 October 2026

**Design response:** [Performance and architecture request](../design/0.9.2-performance-and-architecture-request.md)

**Research response:** [Dead code detection](../research/2026-10-24-dead-code-detection.md)

The next planned package version is **0.9.2**, following the published 0.9.1. The completed
self-review should supply evidence for that work. Its stage counts and scores must be understood
and checked against actual code before becoming recommendations.

## Requested changes

- Fix the two Fresh Eyes prompt/validation failures that needed operational clarification, and
  the 55-minute taxonomy bottleneck. Investigate the actual cause instead of treating more model
  capacity as the only remedy.
- Make Pattern analysis examine every module for every catalogue pattern. A logical economical
  specialist owns one pattern and systematically asks where that pattern would help, including
  a useful rewrite or abstraction. Preserve all catalogue families; the agent-provider contract
  example remains one of many possible patterns.
- Support many more concurrent economical workers, including 50 or 100 where practical. Find
  independent work currently serialized. Models can be escalated automatically after weaker ones
  fail, while preserving completed work and continuing toward task completion.
- Explain what the 27 alternatives across nine scopes actually proposed, what their comparisons
  established and which concrete code improvements follow. A final review marked complete is not
  itself useful architectural advice.
- Build the initial dependency/function/interface graph quickly. Parsing imports, references,
  functions and counts should be deterministic work; slower semantic understanding should not
  block access to that graph.
- Make the project substantially smaller and easier to understand. A semantic graph redesign
  should not leave unnecessary old machinery behind or keep increasing source files and lines.
  Investigate dead code and duplicate active mechanisms; seriously test a roughly half-sized
  implementation rather than accepting the current code volume as inevitable.
- Preserve a lean, intelligible product whose primary function is a graph and concise semantic
  guide to a repository. Avoid extensive prose, unnecessary services and extra coordination.
- Fresh Eyes must reason from functionality without seeing current source or being confined to
  the current design. Knowing what a product does should allow a modern alternative implementation,
  even when its existing implementation is radically outdated.
- Turn those alternatives into a source-aware comparison and concrete retain/change/delete plan
  after the blind design stage. Keep the user's useful workflow experience and optional steering.
- Rewrite the README, PyPI description and other product-facing text after implementation so
  they accurately describe the real system, its workflows, defaults and limitations.

## The TV analogy

The maintainer describes observing the output and controls of a TV without knowing its internals.
If the existing TV uses decades-old technology, a designer should still propose an appropriate
modern implementation from the required viewing experience. It should not reproduce the old
technology merely because the input description inherited its components or constraints.

Applied to AnaxiGraph, Fresh Eyes should know that the product builds a useful repository graph,
explains behavior and supports architecture work. It should challenge how much code, storage,
coordination and machinery those functions actually require. A large box labelled "engine" does
not demonstrate a smaller implementation.

## Explicit follow-up on dead code

The maintainer rejects a 90-day age requirement as a condition for finding unused code. Long-lived
unchanged code can be healthy and used; freshly replaced code can already be dead. Research how
established tools find dead code, apply suitable methods to AnaxiGraph, and use the results to
identify real retirement opportunities. Age must not stand in for usage or prevent this audit.

The maintainer also emphasizes understanding the audit itself: distinguish observed defects,
recommendations supported by inspected source, incomplete evidence, and speculative design targets.
Do not turn model scores or a large number of completed stages into a claim that the architecture
is good, novel, complete or minimal.
